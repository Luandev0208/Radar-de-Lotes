RADAR DE LOTES - TUTORIAL COMPLETO DE CONFIGURACAO E PUBLICACAO
================================================================

Este tutorial e para o computador de DESENVOLVIMENTO. O computador que apenas
usa o Radar nao precisa de Python, Git, GitHub CLI, Inno Setup nem VS Code.

A. PROGRAMAS NECESSARIOS
------------------------
1. Python 3.12 64-bit
   - Baixe pelo site oficial do Python.
   - Marque a instalacao do Python Launcher (`py`).
   - Confira no Prompt de Comando: py -3.12 --version
   - Uma versao diferente, como 3.14, nao sera usada pelo build.

2. Git
   - Instale o Git for Windows com as opcoes padrao.
   - Confira: git --version

3. GitHub CLI
   - Instale o programa oficial `gh`.
   - Confira: gh --version

4. Inno Setup 6
   - Instale o Inno Setup 6.
   - Os BAT procuram ISCC.exe automaticamente em Program Files.

5. VS Code e opcional. Ele ajuda a editar, mas nao participa do instalador.

B. CONECTAR O GIT AO GITHUB
---------------------------
No Prompt de Comando, execute:

  git --version
  gh --version
  gh auth login

No assistente do `gh`, escolha GitHub.com, HTTPS e login pelo navegador.
Nunca coloque token dentro de BAT. Depois confira:

  gh auth status

C. CLONAR OU CONFERIR O REPOSITORIO PRIVADO
-------------------------------------------
Para clonar em uma pasta nova:

  gh repo clone Luandev0208/Radar-de-Lotes
  cd Radar-de-Lotes

Para conferir uma pasta existente:

  git remote -v
  git status
  git branch

O origin correto e o repositorio privado Luandev0208/Radar-de-Lotes.
Se for necessario corrigir:

  git remote set-url origin https://github.com/Luandev0208/Radar-de-Lotes.git
  git fetch origin

D. PRIMEIRA CONFIGURACAO
-----------------------
1. Mantenha PROJETO e AUTOMACOES juntas dentro da raiz Radar-de-Lotes.
2. Abra AUTOMACOES\RADAR.bat.
3. Use a opcao 14 - Verificar ambiente.
4. Use a opcao 2 - Rodar testes. A `.venv` sera criada automaticamente.
5. Use a opcao 5 - Preparar versao completa para teste.
6. O Inno Setup sera chamado sem abrir sua interface.
7. Instale o arquivo em ENTREGA_PARA_TESTE numa maquina de teste.

E. COMECAR UMA NOVA VERSAO
--------------------------
1. Garanta que nao existem alteracoes soltas.
2. Abra RADAR.bat e escolha 6.
3. Informe a proxima versao no formato X.Y.Z.
4. O script atualiza main e cria dev-vX.Y.Z.
5. VERSION recebe X.Y.Z-dev e e commitado na branch.
6. Programe e faça commits somente nessa branch.

F. PREPARAR A VERSAO PARA TESTE
------------------------------
1. Na branch dev, abra RADAR.bat.
2. Escolha 5.
3. O processo para imediatamente se um teste ou build falhar.
4. Envie o instalador de ENTREGA_PARA_TESTE para teste.
5. Nao publique antes da aprovacao explicita.

G. PUBLICAR DEPOIS DA APROVACAO
-------------------------------
1. Volte a branch dev aprovada e deixe o Git limpo.
2. Abra RADAR.bat e escolha 15.
3. Confira branch e versao.
4. Digite exatamente PUBLICAR.
5. O fluxo repete testes/build, transforma a versao em final, cria
   backup-vVERSAO-ANTIGA e atualiza main.
6. O push da main dispara o GitHub Actions. Somente ele roda os testes finais
   em ambiente limpo, compila, calcula SHA-256 e cria a tag/Release privada.
7. O BAT 10 apenas acompanha o workflow e abre a Release pronta; ele nunca cria
   uma segunda tag ou Release concorrente.
8. A branch dev nao e apagada automaticamente.

Nas proximas versoes a aprovacao explicita e obrigatoria. A permissao especial
usada na criacao inicial destas automacoes nao muda essa regra.

H. VOLTAR UMA VERSAO COM SEGURANCA
----------------------------------
As branches backup-vX.Y.Z apontam para estados antigos aprovados. Primeiro:

  git fetch origin
  git branch -a
  git log --oneline origin/backup-vX.Y.Z -5

Para inspecionar sem mudar main:

  git switch -c restauracao-vX.Y.Z origin/backup-vX.Y.Z

Teste essa branch. Nao use push forcado nem apague main. Para restaurar main,
faca uma revisao/merge consciente somente depois de confirmar a versao correta.

I. ATUALIZAR O COMPUTADOR DO USUARIO
------------------------------------
Depois que a Release privada estiver publicada:
1. O Radar verifica atualizacoes no maximo uma vez por dia.
2. O usuario clica Atualizar agora.
3. O programa baixa o instalador, confere SHA-256, fecha e instala.
4. A nova versao reabre e confirma o sucesso.
5. O instalador temporario usado e arquivos antigos da pasta temporaria
   controlada pelo Radar sao removidos. Downloads e Desktop nao sao tocados.

J. SOLUCAO DE PROBLEMAS
-----------------------
Python 3.12 nao encontrado:
- Instale a versao 64-bit com o Python Launcher. Teste `py -3.12 --version`.

PyInstaller/dependencias:
- Execute a opcao 2; ela recria/atualiza o ambiente necessario.

Inno Setup nao encontrado:
- Instale Inno Setup 6. Se estiver em pasta diferente, defina ISCC_PATH antes
  de executar o BAT ou ajuste somente o caminho em AUTOMACOES\config.bat.

Git nao instalado ou repositorio incorreto:
- Instale Git, clone novamente com `gh repo clone` e confira `git remote -v`.

GitHub CLI nao autenticado:
- Execute `gh auth login` e depois `gh auth status`.

Main ou branch suja:
- Confira `git status`. Faça commit consciente ou guarde a alteracao antes.
  Nao apague arquivos apenas para fazer o script passar.

Branch errada:
- Desenvolvimento deve ocorrer em dev-vX.Y.Z; Release final deve sair de main.

Testes falhando:
- A publicacao e bloqueada. Corrija o erro e rode os testes novamente.

Tag ou Release ja existe:
- Confira VERSION e o log do GitHub Actions. O BAT local nao cria nem substitui
  Releases; a publicacao oficial pertence exclusivamente ao workflow.

Sem internet:
- Git, gh e Release falharao com segurança. Tente de novo quando a conexao voltar.

Erro ao criar backup:
- Pare. Confira se backup-vX.Y.Z ja existe e se origin/main esta acessivel.

Erro durante a publicacao:
- Leia AUTOMACOES\logs e `git status`. Nao repita comandos destrutivos.
- Os scripts preservam a branch dev e o backup existente.

RESUMO
------
Uso diario: abra AUTOMACOES\RADAR.bat e escolha uma opcao.
Antes de alterar: opcao 6.
Antes da aprovacao: opcao 5.
Depois da aprovacao explicita: opcao 15 e digite PUBLICAR.
